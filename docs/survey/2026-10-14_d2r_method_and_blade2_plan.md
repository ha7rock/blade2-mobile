# D2R Mobile 方法拆解与 Blade2 iOS 移植方案

研究日期：2026-10-14。源码基线：`jhaizhou-ops/d2r-mobile`，提交 `615a429a290df18e257a435a5ca3219d6c8d2fb0`。

目标：将 NAS3 中的 Blade II 做成可在用户自己的 iPhone/iPad 离线运行的应用。挂载后实际文件为 `/Volumes/Downloads/Blade II - The Return of Evil [01009CC00E224000] [v131072] (1G+1U).xci`，大小 3,002,950,656 字节。已读取并确认 XCI 的 HEAD 与 HFS0 分区标记；现已成功合并本体与更新并提取程序及资源，确认主程序含 `++UE4+Release-4.17` 和 `nvnBootstrapLoader`；这是一份 UE4 4.17 系列的 Switch ARM64 构建，尚未在 iOS 执行。

## 1. 核心思想：保留游戏，替换平台边界

D2R Mobile 的关键前提是原始程序来自 Switch ARM64，目标 Apple Silicon 同样执行 ARM64 指令。项目保留大部分机器码，把平台不兼容性集中到离线改写器、装载器、系统服务实现和图形翻译层。

它是针对一个游戏及特定版本的兼容工程。源码中的游戏函数地址、数据布局、着色器事实表、资源生成器和触控逻辑都构成适配成本；这些不能通过替换游戏名自动迁移。

调用链：

```text
原始 ARM64 游戏模块 → 离线指令改写 → 编入已签名 iOS 可执行文件
                                     ↓
                         装载、重定位、系统服务接管
                                     ↓
游戏 NVN 调用 → 命令记录 → Metal 重放 → CAMetalLayer
原始 GPU 着色器 → SPIR-V → MSL → metallib ─────┘
触控事件 → 游戏语义操作 → 原游戏 UI / 世界交互入口
```

### CPU 与装载

`dm/tools/patch_nso.py` 解压 NSO、重建内存映像，改写 x18、线程寄存器、系统调用和计时器访问。补丁跳进宿主门，由 `dm/host/entry.S` 保存寄存器、`hle.c` 分派，再恢复游戏执行。

这里最值得复用的约束是“按版本登记、验证原字节、遇到不匹配立即停止”。`CUTS` 保存原字节、替换字节及原因，`OBS` 注册观测点。通用指令改写与游戏行为修改必须区分：后者需要单独的行为验证，不能宣称所有修改都与原版等价。

`dm/ios/tools/gen_embed.py` 把原代码和补丁区放进 Mach-O 的 `__TEXT`，可写数据另放。`loader.c` 的 iOS 分支使用 `vm_remap` 恢复模块原来的相对布局，共享已签名代码页，处理数据重定位。这解释了为什么该路线不需要在手机上动态生成游戏机器码。仅有相同 ISA 仍不够，还要解决 ABI、线程、内存布局、符号解析和代码签名。

### 系统服务：选择合适的接管层级

`hle_svc.c`、`hle_thread.c` 承接底层内存与线程调用，让原 SDK 中可以保留的实现继续运行；兼容的 libc 函数直接对接宿主；文件、输入、音频等服务则在 SDK 接口处接管。`HLE` 与 `HLE_FORCE` 分别处理缺失导入与强制替换。

这是一种降低重写范围的方法：优先保留已经正确的逻辑，只替换平台边界。但返回 0 的未实现接口并不代表兼容成功；新游戏必须记录实际调用覆盖率，并逐项处理被调用的缺口。

### 图形：API、数据布局、着色器三条线同时适配

`nvnBootstrapLoader` 是图形接管入口。`dm/gfx/nvn/hle_nvn.c` 记录命令，`nvn_mtl.m` 将命令重放为 Metal。纹理需要从 Tegra block-linear 布局转换，GPU 完成事件必须对应真实 Metal 执行完成，不能只让函数“返回成功”。

源码文档列出 523 个取得地址的 NVN 名称，其中游戏主程序有调用点的 216 个包含 203 个语义实现与 13 个空实现。其余接入报错桩。这说明它覆盖的是 D2R 使用面，而非完整通用 NVN 驱动。

着色器链为 Maxwell 机器码 → Ryujinx 翻译库产生 SPIR-V → spirv-cross 产生 MSL → Metal 编译器生成 metallib。资源绑定、纹理维度、输出类型等并不总能从机器码恢复，项目通过 `shader_facts.tsv` 等事实表补足。新游戏必须重新建立这些输入事实和管线预热清单，不能复用 D2R 的 shader 哈希表。

有 Mac/Xcode 的主路线离线编译；仓库另有无 Metal 编译器路线，把 MSL 打包后在设备首次编译。因此“所有路线都完全没有设备端 shader 编译”不是准确概括。

### 交互：重用原游戏语义

`dm_cursor.c`、`dm_world.c`、`dm_actions.c` 等将触摸映射到原游戏的控件消息、点击世界、购买出售等入口；这比仅叠加虚拟按键更接近手机体验。切换手柄与触屏还有独立状态机，避免旧输入残留。

这些模块大量依赖 D2R 的结构与地址。Blade2 可借鉴“输入 → 语义动作 → 原逻辑”的分层，但必须先确定它自己的交互入口。首个可玩版本应先保证移动、攻击、菜单、保存，再改造触控体验。

## 2. 真正值得迁移的方法论

1. **锁定输入。** 记录版本、程序架构、文件清单、关键文件哈希。补丁只对已经验证的输入生效。
2. **建立原版基线。** 固定存档、输入序列、随机种子和可控时钟，保留截图、状态和存档结果。
3. **先闭合最小执行链。** 程序入口、资源加载、第一帧、可交互场景、保存重载逐级推进。
4. **把不兼容性集中。** 使用平台服务适配层、渲染后端、输入层，避免到处散布特殊分支。
5. **把昂贵工作移到构建期。** 指令改写、着色器转换、纹理转换和资源索引尽量提前完成；缓存必须与输入和工具链版本绑定。
6. **使用可失败的验证。** 除正常样本外，主动损坏补丁和资源，确认检查器确实能发现错误。
7. **先保持行为，再添加功能。** 将移植正确性、移动端交互变化和玩法扩展分开验收。

仓库的 `structck.py` 验证结构，`equiv.py` 用多组输入比较原指令与补丁块的寄存器、内存和异常，`gatefn` 验证门调用约定。游戏级另有逐拍状态、存档、截图、触控及保存失败测试。随机差分测试是强证据，但不是对所有可能执行状态的数学证明。

完整验收依赖原游戏文件、标准存档、原版运行参考数据，以及未公开的部分驱动工具。公共仓库自测通过不能代替真机游戏验收。README 的帧率、功耗和内测覆盖是作者报告，本次未复测。

## 3. Blade2 的决策必须由文件证据驱动

| 发现的输入 | 优先路线 | D2R 方法的适用部分 |
|---|---|---|
| 完整引擎源码项目 | 使用引擎的 iOS 构建链，移植原生插件、输入与资源 | 边界隔离、离线资源处理、回归方法；通常不需二进制改写 |
| Switch ARM64 可执行模块与资源 | 评估 NSO 改写、Horizon 服务与 NVN 适配 | 最接近原项目，但仍需新游戏的符号、接口、着色器与布局调查 |
| Windows x86/x64 安装目录 | 先确认源码或可移植引擎是否存在；否则另做 CPU/Windows API/图形层可行性验证 | 同 ISA 原生执行前提不成立，不能仅改 NSO 脚本 |
| Android APK / ARM64 原生库 | 检查 Java/JNI、Bionic、系统服务、图形与资源依赖，优先寻找原项目 | ARM64 只是部分条件，Android 程序不能直接当 iOS 程序加载 |
| 只有美术、资源包或存档 | 还需对应执行程序或兼容引擎 | 资源本身不包含可完整运行的游戏逻辑 |

对 Windows 程序，静态重编译是否可行还取决于间接跳转、异常、自修改代码、动态模块和运行时生成代码等；必须做真实样本验证，不能承诺一键转换或某个固定性能。

## 4. 面向私人离线安装的实施验收

| 阶段 | 实际产出 | 通过条件 |
|---|---|---|
| 文件调查 | 目标目录清单、架构/引擎识别、依赖与缺口表 | 已读取真实程序，移植路线有证据 |
| 最小运行 | 能运行游戏核心的宿主或引擎构建 | 原资源加载成功、进入真实场景，不是静态展示壳 |
| 画面与声音 | 渲染后端、音频和资源转换 | 关键场景与原版对照，缺失接口可追踪 |
| iOS 构建 | 可签名应用、资源导入、沙盒存档、生命周期处理 | iPhone/iPad 真机启动、触控可玩、保存重载 |
| 离线与稳定性 | 飞行模式流程、后台恢复、长时间运行记录 | 不依赖 NAS 或电脑执行游戏，资源与存档在设备本地 |

NAS 是输入来源，最终设备离线运行意味着需要把所需资源放进 App 或导入设备沙盒。不能让运行时继续依赖 NAS 的路径。

设备型号、系统版本和签名配置将在有可构建目标后核对。签名成功、安装成功、游戏可玩是三个不同的验收点。

## 6. Blade II 实际模块调查与改写实验

已编译 hactool（提交 `1d64a83450e025622f3468c28fc4164dad2c5ef6`），提取本体与更新，更新程序 NCA 报告 SDK 7.4.0.0。主程序 build ID 为 `0379ac316b16fbc1a00d2f0dc139ffa9`（前 16 字节）。

| 模块 | 代码段大小 MiB | 导入符号数 | 与 D2R 字面 HLE 注册匹配数 |
|---|---:|---:|---:|
| rtld | 0.01 | 19 | 0 |
| main | 66.74 | 608 | 103 |
| subsdk0 | 3.45 | 647 | 19 |
| sdk | 5.18 | 13 | 0 |

以上只说明符号名称，不说明函数行为、参数 ABI 或线程语义兼容。许多导入由原 SDK 导出满足，不需要逐项重写；反过来，名称匹配也不能证明 D2R 的实现足够。扫描器不展开 C 宏，因此它不是完整链接器。

主程序中找到 513 个 NVN 名称字符串，其中 512 个在 D2R 名称表中，剩下的 `nvnBootstrapLoader` 是入口。这是 API 家族接近的证据，但不能把 512/513 解读为图形兼容率；名称存在不等于会调用，更不等于对应实现完整。

资源核心 `BladeII-Switch.pak` 大小 1,896,213,638 字节，footer 标记匹配 UE Pak，版本字段为 4，索引 5,242,696 字节且范围合法。现阶段仅检查 footer，未完成 shader 提取或资源解码正确性验证。影片目录包含多种 MP4；D2R 的空视频实现不能作为 Blade II 视频完整支持。

### 实际阻碍一：不同的间接跳转形态

在隔离环境安装参考项目指定的 capstone 5.0.9、lz4 4.4.5、unicorn 2.1.4，直接以 `DM_RULESET=native` 测试原改写器。

主程序改写实际失败：`AssertionError: jump table 29329c8`。该位置的形态是 `ldrsw` 读有符号 32 位表项，再与表基址相加得到 x18，最后 `br x18`。原脚本只识别其预设的另一类跳转表形态，因此拒绝改写。

不能删除断言继续：x18 在 Apple 平台不能按原用法保留，必须恢复该表的基址、界限和目标集合，设计保留寄存器及跳转语义的替换，再做正负对照差分测试。

### 实际阻碍二：追加补丁布局超出直接分支距离

主程序含 BSS 的原映像末尾为 `0x82c1000`。原算法会把补丁放到 `0x82d0000`。代码偏移 `0x1192c` 已有 `ldp w18, w0, [x17]`，到补丁起点距离为 137,094,868 字节，大于 B 指令正向范围上限 134,217,724 字节。

这是独立静态检查发现的布局约束；实际改写运行先在跳转表识别处失败，尚未执行到该分支断言。后续需重设补丁区布局或引入经过验证的近端跳板，连同签名代码嵌入、装载器和等价检查一起调整，不能只修改分支编码掩码。

### 已走通的局部步骤

SDK 模块的离线改写已生成产物：5 个独占窗口、11,106 处普通 x18 改写、148 处条件分支、43 处 PC 相对操作，以及线程寄存器/计时器/系统调用适配；补丁区 458,176 字节，92 个宿主门，未套用 D2R 游戏专用 cuts 或 OBS。产物生成不等于能启动 SDK，仍需行为验证、Horizon 服务和初始化次序适配。

### 后续实现顺序

1. 将改写布局与 D2R 游戏规则分离，补上 Blade II 的间接跳转形态和大映像分支策略。
2. 在 Mac 宿主先验证模块装载、SDK 初始化、原构造函数与 `nnMain`；移除 D2R 专用地址依赖，未支持服务明确失败。
3. 读取 UE4 Pak 索引及 shader 数据，建立 Blade II 的资源反射和 NVN 调用覆盖；先出真实首帧，再做完整场景。
4. 验证原版离线玩法、输入、音频视频与保存；最后接 iOS 外壳、签名、设备资源导入和生命周期。

目前达到的是可复核的输入调查与局部改写实验，不是可玩的 iOS 应用。仍存在实质性的二进制兼容层开发工作。
